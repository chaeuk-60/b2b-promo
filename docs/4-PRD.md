# PRD: b2b-promo

## 0. 문서 정보
| 항목 | 내용 |
|---|---|
| 기반 문서 | `docs/1-domain-definition.md` |
| 작성일 | 2026-08-13 |
| 버전 | v2.0 |

## 1. 배경 및 목적
- **문제#1**: 회사가 프로모션을 제공해도 신청 경로가 불편해 참여율이 낮다.
- **문제#2**: 재방문(MAU) 유인이 없어 사용자가 프로모션을 놓치거나 앱을 잊는다.
- **목적**: 프로모션 신청/찜 기능과 펫(다마고치) 육성 기능을 결합해, 신청 경로를 단순화하고 재방문을 유도하는 웹 앱을 만든다.

## 2. 목표 사용자 및 비즈니스 목표
- **목표 사용자**: 프로모션을 신청하는 거래처 담당자(개인 계정 기반). 3000개 이상 거래처가 등록되어 사용하는 것을 목표로 한다.
- **비즈니스 목표**: 등록 거래처 중 1000개 이상이 프로모션 기능(신청/찜)을 이용하는 것.
- **경쟁사 분석("일정 변경 시 채팅 이력으로 근거 남김")**: 팀 캘린더/협업 툴을 전제로 한 문구로, b2b-promo(프로모션 신청·펫 육성) 도메인에는 해당 없음. 본 앱에는 일정 변경 기능 자체가 없고(신청 취소도 미제공), 채팅 이력 관리도 범위 밖.

## 3. 범위
### 3.1 In Scope (이번 3일 개발 범위)
- 회원가입/로그인 (이메일 + 비밀번호)
- 프로모션 목록/상세 조회
- 프로모션 신청 / 찜 토글
- 펫 조회 및 육성(목욕/밥/쓰다듬기, 성장 단계 전이, 특식 급여, 오늘의 운세)
- 로그인 시 mood/eggState 랜덤 부여, 하루 단위 리셋(자정 기준)
- 선물(할인 쿠폰) 지급 로직(성체 5% 확률 + 3일 쿨다운, 성체 순환 시 100%)
- 반응형 웹 UI(모바일 브라우저 대응)

### 3.2 Out of Scope
- 결제, 배송, 실제 쿠폰 사용/환불 처리
- 신청 취소 기능(담당자 문의 안내로 대체)
- 팀/조직 단위 계정, 권한 관리, 협업 기능 — 해당 없음(본 앱은 개인 계정 기반)
- Google Calendar, Slack 등 외부 서비스 연동 — 현재 미적용(추후 적용 예정)
- 모바일 네이티브 앱(반응형 웹으로만 대응)

## 4. 플랫폼 및 기술 스택
| 구분 | 내용 |
|---|---|
| 플랫폼 우선순위 | 웹 우선. 모바일은 별도 앱 없이 반응형 UI로 대응 |
| 프론트엔드 | React 19 |
| 전역 상태관리 | Zustand |
| 백엔드 통신 | TanStack Query |
| 백엔드 | Node.js + Express |
| DB 드라이버 | pg |
| 데이터베이스 | PostgreSQL 17 |
| 인증 | JWT (액세스 토큰 + 리프레시 토큰) |
| 외부 연동 | 없음(추후 Google Calendar, Slack 등 적용 예정이나 이번 범위 아님) |

## 5. 핵심 기능 요구사항
### 5.1 회원가입/로그인/인증
- 이메일/비밀번호로 가입, 비밀번호는 해시 저장
- 가입 시 펫 1마리 자동 생성(알 상태, activityCount=0)
- 로그인 시 mood/eggState 랜덤 재설정, lastActiveAt 갱신, 접속 횟수 카운트(자정 기준)
- **인증 방식**: JWT 기반 액세스 토큰 + 리프레시 토큰
  - 로그인 성공 시 액세스 토큰(짧은 만료, 예: 15분)과 리프레시 토큰(긴 만료, 예: 14일)을 함께 발급
  - 액세스 토큰은 API 요청마다 `Authorization: Bearer` 헤더로 전달, 만료 시 401 응답
  - 리프레시 토큰으로 액세스 토큰 재발급 엔드포인트 제공(리프레시 토큰 자체는 httpOnly 쿠키로 저장해 XSS 노출 최소화)
  - 리프레시 토큰은 서버에 별도 저장하지 않는 스테이트리스 방식으로 시작(로그아웃 시 즉시 무효화·강제 만료는 이번 범위 밖) — ponytail: 단일 서버·소규모 트래픽 전제, 다중 기기 강제 로그아웃/토큰 폐기 목록이 필요해지면 리프레시 토큰 저장 테이블(또는 Redis 블랙리스트) 도입

### 5.2 프로모션 신청/찜
- 프로모션 목록/상세 조회 (title, 기간, 내용)
- 찜 토글: 목록/상세 어디서나 즉시 반영
- 신청: 기간 내에만 가능, 중복 신청 방지, 신청 시 해당 특식 보유
- 신청 취소는 미제공, "취소는 담당자에게 연락 주세요" 안내만 표시
- 기간 종료된 프로모션은 신청 버튼 비활성화 + "담당자에게 연락 주세요" 안내

### 5.3 펫 육성
- `1-domain-definition.md` 5장(상태), 6장(비즈니스 규칙)에 정의된 전이 규칙을 그대로 구현
  - 알 → 새끼 → 성체 성장 전이 및 50% 확률 판정
  - 성체 순환(2주) / 사망(7일 미접속, 우선 적용) / 묘비 → 새 알
  - eggState / mood 전이(목욕, 밥, 쓰다듬기)
  - 특식 요청(requestedPromotionId 선정: 찜만 한 프로모션 70% 가중치) 및 급여 시 무지개 변화
  - 자발적 급여 시 10% 특수효과(진화 50% / 반짝이 50%)
  - 하루 3회 이상 접속 시 mood "행복" + 모션
  - 오늘의 운세(하루 1회, 새끼/성체 전용)
  - 선물(할인 쿠폰) 지급: 성체 5%(3일 쿨다운) / 성체 순환 100%

### 5.4 반응형 웹 UI
- 데스크톱/모바일 브라우저 모두 단일 코드베이스(반응형 레이아웃)로 대응
- 별도 모바일 전용 화면/컴포넌트 분기는 두지 않음(오버엔지니어링 금지 원칙)

## 6. 데이터 모델
`1-domain-definition.md` 3장(엔티티), 4장(관계)을 그대로 따른다. 이번 PRD에서 별도로 추가/변경하는 엔티티는 없다.

## 7. 성공 지표(KPI)
| 지표 | 정의 | 비고 |
|---|---|---|
| 거래처 등록 수 | 가입 완료한 거래처(사용자) 누적 수 | 목표: 3000개 이상 |
| 프로모션 기능 이용 거래처 수 | 신청 또는 찜을 1회 이상 수행한 거래처 수 | 목표: 1000개 이상 |
| 프로모션 신청 전환율 | (신청 수 / 프로모션 조회 수) | 문제#1 대응 |
| DAU/MAU | 일별·월별 순 접속 사용자 수 | 문제#2 대응 |
| 하루 3회 이상 접속 비율 | 전체 접속 사용자 중 "행복" mood 도달 비율 | 재방문 유도 효과 측정 |
| 펫 생존율 | 7일 미접속으로 사망(묘비 전환)하지 않은 펫 비율 | 재방문 유도 효과 측정 |

## 8. 일정 및 리소스
| 항목 | 내용 |
|---|---|
| 개발 기간 | 3일 (핵심 기능 완성 기준) |
| 팀 구성 | 1인 개발 |
| 예산 | 1인 개발 규모 |

3일 내 완성을 위해 결제/배송/취소/외부 연동/팀 기능은 전부 Out of Scope로 제외한다(4장, 3.2절 참고). 팀 단위 계정, 캘린더/Slack 연동 등은 도메인과 무관하거나 추후 적용 예정이므로 이번 범위에 반영하지 않는다.

## 9. 접근성 및 사용자 경험
- 접근성: 이번 프로젝트에서는 고려하지 않는다.
- 페르소나별 상세 시나리오: 생략(개인 사용자가 로그인 → 프로모션 확인/신청/찜 → 펫 육성의 단일 플로우를 따름).
- 모바일: 별도 앱 없이 반응형 웹 UI로만 대응.

## 10. 리스크 및 제약
| 리스크 | 내용 | 대응 |
|---|---|---|
| 일정 리스크 | 1인 개발, 3일이라는 짧은 기간 | Out of Scope 항목 엄격히 배제, 핵심 플로우(신청/찜/펫 육성)만 구현 |
| 규칙 복잡도 | 펫 상태 전이 규칙(확률, 하루 단위 리셋 등)이 다수 | 도메인 정의서의 규칙을 그대로 구현하고 임의 확장 금지(오버엔지니어링 금지 원칙 준수) |
| 확장성 리스크 | 목표 거래처 수(3000개 등록, 1000개 이용)에 따른 트래픽 증가 | 이번 범위에서는 별도 스케일링 설계 없이 PostgreSQL 17 기본 구성으로 대응, 필요 시 추후 검토 |
| 보안 리스크 | 리프레시 토큰을 서버에 저장하지 않는 스테이트리스 방식(5.1절)이라 로그아웃 시 즉시 무효화·강제 만료가 불가 | 이번 범위에서는 액세스 토큰 짧은 만료(15분)로 노출 최소화, 다중 기기 강제 로그아웃이 필요해지면 리프레시 토큰 저장 테이블(또는 Redis 블랙리스트) 도입 |
